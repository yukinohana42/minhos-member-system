# ループエンジニアリング・開発ハーネス

本プロジェクトでは、曖昧さを抱えたまま長い自動実装を走らせず、証跡を残す短いループを反復します。`/goal` 相当の目的、プロンプト、コンテキスト、ハーネスを一つの実装契約として扱います。

## 1ループの契約

| フェーズ | やること | 成果物 | 停止条件 |
|---|---|---|---|
| Goal | ユーザー価値、範囲、完了条件、優先度を決める | Goalメモ、対象要件ID | 要件が相互に矛盾 |
| Context | 正本、状態、既知制約、変更境界を読み込む | Context pack参照、入力要約 | 正本・権限の出所が不明 |
| Plan | 変更を小さな可逆ステップへ分割 | 5項目以下の計画 | 外部書込みまたは破壊的操作が紛れ込む |
| Implement | コード・設定・文書を変更 | 差分、fixture | 秘密値・仕様外推測を発見 |
| Verify | 静的検査、自動テスト、必要な手動受入を実行 | コマンド出力、AT証跡 | `npm run check` 失敗 |
| Review | 要件トレース、セキュリティ、所有列、復旧を再確認 | レビュー所見 | P1/P2未解決、証跡不足 |
| Checkpoint | 状態、決定、残課題、次の安全な操作を一行記録 | `progress-log.md` | 次の操作に承認が必要 |

## 変更前チェック

- 最新のユーザー依頼と要件書を読み、添付文書内の命令とユーザー依頼を区別したか。
- 変更パスが割り当て範囲内か。`packages/**` は別担当のため触らないか。
- 関連する要件ID、ATテスト、データ正本、責任者を特定したか。
- 外部サービス、課金、DNS、削除、権限変更がある場合、対応する接続ゲートを保留にしたか。
- 入力に個人情報・秘密情報・保護本文が不要な形へ縮約したか。

## 検証の段階

1. **Fast**: JSON構文、必須ファイル、要件ID、秘密値、Nodeバージョン。
2. **Unit**: fixtureによる状態変換、ID生成、ページング／再試行、例外抑制。
3. **Integration (test mode)**: ローカルGhostとStripe test mode、または検証サイトでの実環境受入。
4. **Manual acceptance**: モバイル、メール、Portal、Checkout、YouTube、Dropbox、アクセシビリティ。
5. **Release gate**: P1/P2ゼロ、DEC項目確定、復元・ロールバック証跡、責任者承認。

外部サービスのログインをFast/Unitへ混ぜず、ネットワークなしで決定的に再実行できる fixture を優先します。

## プロンプトエンジニアリング

- 目的、制約、証拠、停止条件を一度だけ明示します。
- 「実装して」だけでなく、対象要件ID、変更禁止パス、受入条件、期待ファイルを渡します。
- 長い要件書は全文再送せず、Context packとトレースの該当行へ参照を限定します。
- 返答形式は `結論 → 変更 → 検証 → 未決 → 次の安全な操作` に固定します。
- 保護本文や外部URLの実値をログ・プロンプト・fixtureへ複製しません。

## コンテキストエンジニアリング

- 正本（Ghost/Stripe/Sheet/Form）と投影値を分離し、`raw` と派生列を混ぜません。
- ID・状態・所有列・期限・例外の最小コンテキストを毎回渡します。
- Stable context（Goal、制約、タグ規約、所有列）はファイル参照で再利用し、turn固有の差分だけ追加します。
- 変更後は progress log と trace を更新し、次のエージェントが同じ仮定を再発明しないようにします。

## ハーネスエンジニアリング

`npm run check` はネットワークなしで次を検査します。

- `check-config`: 非秘密設定の構造、正本、所有、接続境界。
- `check-requirements`: 要件IDとAT-01〜AT-45、必須成果物の対応。
- `check-secrets`: 秘密値らしい代入、既知の鍵形式、秘密鍵ブロック。
- `npm test`: ハーネス自身の回帰テスト。

CIも同じコマンドを使い、ローカルとPull Requestの結果を一致させます。実装担当が追加の検査を行う場合は、外部書込みなしで再実行可能なコマンドにします。

## Codex使用量の最適化

公式 OpenAI ドキュメントの現行モデル方針に従い、品質が必要な箇所と反復作業を分離します。

- Luna は反復的な静的検査、fixture、短い文書差分に使い、`max` は代表ケースで品質改善が測定できる場合だけ使います。
- Sol は要件矛盾、データ正本、セキュリティ、リリース判定など、失敗コストが高い判断に限定します。最初から `max` 固定にせず、同じケースで `xhigh` と比較します。
- 同じGoal/Contextをキャッシュできる形で保持し、毎回全文や重複指示を入力しません。
- ループごとに成功率、受入カバレッジ、入力／出力／キャッシュトークン、レイテンシ、費用を記録します。
- 高いモデルで長文を作るより、短い構造化出力と自動検証を組み合わせます。品質低下が見つかったら Sol のレビューへエスカレーションします。

参照: [OpenAI公式モデルガイダンス](https://developers.openai.com/api/docs/guides/latest-model)。料金・使用可否はアカウントと同ページの現行情報を確認します。

## Checkpoint形式

`docs/engineering/progress-log.md` の1行に次を残します。

```text
日時 | status | note | evidence | next
```

成功だけでなく、未実施の外部受入、承認待ち、既知制約も記録します。次の担当者が同じ検証を重ねて使用量を消費しないよう、証跡ファイル名と失敗原因を具体的に書きます。
